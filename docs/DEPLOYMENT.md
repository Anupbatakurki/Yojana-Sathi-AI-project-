## 1. Prerequisites

| Need | Where |
|---|---|
| Python 3.11+ and Git | python.org, git-scm.com |
| Docker Desktop (for `make up`) | docker.com |
| A GitHub account | github.com |
| A free LLM key | https://console.groq.com/keys |
| A Render account (Option A) | https://render.com — sign in with GitHub |

Before deploying, open https://console.groq.com/docs/models and confirm `openai/gpt-oss-120b` is still a **production** model. If it isn't, use the current production model ID wherever `LLM_MODEL` appears below.

## 2. Verify locally

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
make install
cp .env.example .env            # set LLM_API_KEY; leave API_KEYS empty for local dev
make check                      # must pass: lint, mypy, 54 tests, coverage ≥85%, eval gate
make up                         # API http://localhost:8000/docs · UI http://localhost:8501
```

On Windows without `make`, run the commands inside the `Makefile` targets directly.

Smoke test the API:

```bash
curl localhost:8000/readyz
curl -X POST localhost:8000/v1/ask -H "X-API-Key: change-me-local-key" \
  -H "Content-Type: application/json" -d '{"question":"loan for street vendors"}'
```

## 3. Push to GitHub and turn on CI/CD

```bash
git init && git add . && git commit -m "Yojana Saathi v2.0.0"
git branch -M main
git remote add origin https://github.com/<you>/yojana-saathi.git
git push -u origin main
```

What happens automatically:

| Workflow | Trigger | Does |
|---|---|---|
| `ci.yml` → quality | every push / PR | ruff, format check, mypy, data validation, `pip-audit` |
| `ci.yml` → test | every push / PR | pytest on Python 3.11 + 3.12, coverage gate, retrieval eval gate |
| `ci.yml` → docker | after both pass | builds both images, boots them, probes health, checks a real answer |
| `ci.yml` → push | `main` only | publishes `ghcr.io/<you>/yojana-saathi-api` and `-ui` tagged `sha-xxxxxxx` and `latest` |
| `codeql.yml` | push / PR / weekly | static security analysis |
| Dependabot | weekly | PRs for dependency, base-image and action updates |

Recommended repo settings (Settings → Branches → add rule for `main`): require the CI checks to pass, require a PR, and block force pushes. Then replace `<your-username>` in the README badge.

## 4. Option A — Render (recommended, free)

Two services: `saathi-api` (FastAPI) and `saathi-ui` (Streamlit), defined in `render.yaml`.

1. Render dashboard → **New → Blueprint** → select your repo → **Apply**.
2. When prompted:
   * `LLM_API_KEY` → your Groq key.
   * `API_URL` (for the UI) → leave blank for now.
3. Wait for `saathi-api` to go **Live**, then copy its URL (e.g. `https://saathi-api-xxxx.onrender.com`).
   Open `<url>/readyz` and check you get `"status":"ok"`.
4. Open `saathi-ui` → **Environment** → set `API_URL` to that URL → **Save** (it redeploys).
5. Open the UI URL and test both tabs. Put both URLs in the README.

Notes:
* `API_KEYS` is generated by Render and shared with the UI automatically — the API is never open to the public without a key.
* `autoDeployTrigger: checksPass` means Render redeploys only after GitHub CI passes on `main`.
* Free instances sleep after ~15 min idle; the first request then takes 30–60 s. Upgrade the API to a paid instance (or ping `/healthz` on a schedule) for demos.
* Region is `singapore` (closest to India). It can't be changed after creation.

## 5. Option B — Any Docker host

Use the images CI publishes to GHCR (make the packages public, or `docker login ghcr.io`):

```bash
# on the server
cat > .env <<'ENV'
ENV=prod
LOG_JSON=true
LLM_API_KEY=...
API_KEYS=<long random string>      # python -c "import secrets;print(secrets.token_urlsafe(32))"
UI_API_KEY=<same string>
ENV

docker run -d --name saathi-api --env-file .env -p 8000:8000 \
  -v saathi-var:/app/var --restart unless-stopped \
  ghcr.io/<you>/yojana-saathi-api:sha-<commit>

docker run -d --name saathi-ui --env-file .env -e API_URL=http://<api-host>:8000 \
  -p 8501:8501 --restart unless-stopped ghcr.io/<you>/yojana-saathi-ui:sha-<commit>
```

Or copy the repo and run `docker compose up -d --build`.

Put a TLS-terminating reverse proxy in front (Caddy, nginx, a cloud load balancer). Example `Caddyfile`:

```
saathi.example.com     { reverse_proxy localhost:8501 }
api.saathi.example.com { reverse_proxy localhost:8000 }
```

Always deploy an immutable `sha-` tag in production, not `latest`.

## 6. Option C — Single-container hosts

With `API_URL` empty, the UI runs the whole pipeline in-process.

**Hugging Face Spaces (Docker)**
1. Create a Space → SDK **Docker** → blank template.
2. Push this repo to the Space, and rename `docker/ui.Dockerfile` to `Dockerfile` at the root (or copy it there).
3. Space **Settings → Variables and secrets**: secret `LLM_API_KEY`; variable `PORT=7860`.
4. Add `app_port: 7860` to the Space's README front matter.

**Streamlit Community Cloud**
1. share.streamlit.io → **Create app** → repo, branch `main`, file `streamlit_app.py`.
2. **Advanced settings**: Python 3.12. Rename `requirements/ui.txt` → `requirements.txt` at the root (Streamlit Cloud only reads that path), or add a root `requirements.txt` containing `-r requirements/ui.txt`.
3. **Secrets**: `LLM_API_KEY = "..."`.

Single-container mode has no separate API, so there is no API auth or API-level rate limit — fine for a demo, but use Option A or B for anything public.

## 7. Production checklist

- [ ] `ENV=prod`, `LOG_JSON=true`
- [ ] `API_KEYS` set to a long random value (the API logs `api_auth_disabled_in_prod` if not)
- [ ] `LLM_MODEL` verified as a current production model
- [ ] HTTPS in front of both services
- [ ] `CORS_ORIGINS` set only if a browser app calls the API directly
- [ ] `/app/var` on a persistent volume (feedback log)
- [ ] Health checks: API `/readyz`, UI `/_stcore/health`
- [ ] Prometheus scraping `/metrics`; alert rules from `monitoring/alerts.yml` loaded
- [ ] Scheme data reviewed against official portals; `last_reviewed` in `schemes.json` updated
- [ ] Branch protection on `main`; CI required

## 8. Releases and rollback

**Release**
1. Open a PR, get CI green, merge to `main`.
2. CI publishes `sha-<commit>` images; Render auto-deploys once checks pass.
3. For a named release: update `version` in `pyproject.toml` and `saathi/__init__.py`, add a `CHANGELOG.md` entry, then `git tag v2.1.0 && git push --tags`.

**Rollback**
* Render: service → **Events** → pick the last good deploy → **Rollback**.
* Docker host: re-run the previous `sha-` tag.
* Data-only bad change: revert the `schemes.json` commit; CI re-validates and redeploys.

Updating lockfiles: edit `pyproject.toml`, then `make lock`, run `make check`, and commit the new `requirements/*.txt`.

## 9. Monitoring and alerts

Local: `make up-monitoring` → Prometheus http://localhost:9090, Grafana http://localhost:3000.

| Metric | Meaning |
|---|---|
| `saathi_http_requests_total{route,status}` | Traffic and error rate per route |
| `saathi_http_request_seconds` | Latency histogram per route |
| `saathi_llm_calls_total{kind,outcome}` | LLM successes / failures (translate, answer, judge) |
| `saathi_llm_seconds` | LLM latency (time to first byte for streams) |
| `saathi_retrieval_seconds` | Retrieval latency |
| `saathi_answers_total{mode,language}` | Answers by mode (`llm` / `extractive` / `no_match`) and language |
| `saathi_feedback_total{rating}` | 👍 / 👎 |
| `saathi_rate_limited_total` | Requests rejected with 429 |

Useful queries:

```promql
sum(rate(saathi_http_requests_total{status=~"5.."}[5m])) / sum(rate(saathi_http_requests_total[5m]))
histogram_quantile(0.95, sum by (le) (rate(saathi_http_request_seconds_bucket{route="/v1/ask"}[5m])))
sum by (mode) (rate(saathi_answers_total[1h]))
```

Logs are one JSON object per line with `request_id`. The same ID is returned in the `X-Request-ID` response header and in every error body, so a user's error report can be traced end to end. Questions are PII-redacted before they reach logs or the feedback store.

## 10. Scaling

| Concern | Today | When you outgrow it |
|---|---|---|
| API replicas | Stateless, scale horizontally | — |
| Rate limiting | In-memory per process | Move to a Redis-backed limiter shared by all replicas |
| Metrics with `WEB_CONCURRENCY>1` | One process per container | Prefer more containers over more workers, or enable `prometheus_client` multiprocess mode |
| Feedback store | JSONL on a volume | A Postgres table |
| Knowledge base | 20 schemes, in memory | Thousands of schemes → a vector DB (pgvector, Qdrant) behind the same `HybridRetriever` interface |
| LLM cost / latency | Per-request calls | Cache answers for identical (question, language) pairs; use a smaller model for translation |

Memory: the embedding model is small (an ONNX model of roughly 130 MB on disk), so a 512 MB instance is the target. Measure your build with `docker stats` and raise the instance size if it gets OOM-killed.

## 11. Runbook

| Symptom | Check | Fix |
|---|---|---|
| `/readyz` stays 503 | Container logs for `pipeline_ready` | Model download blocked → images bake the model at build time; rebuild, or set `USE_DENSE=false` |
| All answers are "showing source text" | `saathi_llm_calls_total{outcome="error"}`, logs `llm_call_failed` | Invalid or expired key, model retired, or provider outage. Rotate the key or change `LLM_MODEL`. Users still get cited extractive answers. |
| Many 429s | `saathi_rate_limited_total` | Raise `RATE_LIMIT_PER_MINUTE`, or check that the UI sends `X-Client-Session` with a valid key |
| UI shows "Can't reach the Saathi service" | UI logs; `API_URL`; API `/readyz` | Wrong `API_URL`, API asleep (free tier), or `UI_API_KEY` not in `API_KEYS` (API returns 401) |
| Wrong or outdated scheme info | Feedback log 👎 entries | Fix `data/schemes.json`, add an eval question, open a PR |
| Key leaked | — | Rotate at the provider, update the env var, redeploy. Rotate `API_KEYS` by listing old and new together, deploy the UI with the new key, then remove the old one. |
